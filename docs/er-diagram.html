01

アカウントと主催者

登録と同時に type=USER の Organizer（個人主催者）を作る。団体を作ると（申請なし）type=GROUP の Organizer ができ、作成者が owner になる。権限は User.role（ADMIN = NMJ 運営 / USER）と団体の owner（複数可）の組み合わせで、admin / owner / user の3種類になる。/@slug はどちらも Organizer.slug。権限判定は canManage(organizerId, userId) に集約する。

ルール

  • Organizer.userId は type=USER のときだけ入る（CHECK 制約）
  • OrganizerMember は type=GROUP の主催者にだけ作る
  • owner は複数可。最後の owner は離脱できない（アプリのトランザクションで検証）

  • 団体の削除・引き継ぎの扱いは未決

  • 追加 GroupJoinRequest：同じ団体のページが増えないよう、既存の団体へ参加を依頼する
  • Auth.js Account / Session / VerificationToken（VerificationToken は関連なしのため図から省略）
02

イベントと申込

申込は Event ではなく Slot にぶら下げる（種類・定員・価格は枠の属性）。イベント全体の上限は Event.capacity。定員判定は Slot（と Event）行を SELECT … FOR UPDATE でロックしてから、参加予定と決済中の確保を数える。申込は「参加予定」か「キャンセル」しか持たない（支払い待ち・補欠はなし）。1人1イベントに QR チケットを1枚発行し、受付の状態はチケットで持つ。申込時の質問は全イベント共通の質問＋主催者の追加質問で、回答だけが個人情報を持つ。

申込の流れ（10/8 改定）

  • 無料枠だけ → その場で CONFIRMED（参加予定）＋ Ticket を発行
  • 有料枠を含む → Payment（PENDING）で席を確保 → 決済完了の Webhook で全枠を CONFIRMED ＋ Ticket。失敗・期限切れは何も作らず席を解放
  • 満員の枠・全体の上限に達したイベントは申し込めない（補欠なし）

ルール

  • 同じ枠に有効な申込は1人1件（部分一意インデックス）
  • 受付の状態はいつでも戻せる。変更はすべて CheckinLog に残す
  • 共通の質問（commonKey あり）は削除・変更不可。公開後は質問の削除・type 変更を禁止
  • 回答は Event.endAt ＋ answerRetentionDays を過ぎたら削除（Registration と Payment は残る）

補足

  • 追加 SavedEvent：保存（旧 Favorite）。保存した人にもお知らせを送れる
  • 追加 Genre・Event.area・Event.capacity・Slot.kind：絞り込みと全体の上限
  • 追加 Ticket・CheckinLog：QR チケットと受付の状態管理
  • 追加 AnswerExportLog：CSV 出力の記録（§8 で必須）
  • 追加 Event.cancelReason、RegistrationQuestion.slotIds
03

決済

MVP はモック決済だが、実決済と同じく Webhook で確定する。決済画面に進んだ時点で Payment（PENDING）を作って席を確保し（holdExpiresAt まで）、PAID の Webhook で初めて Registration と Ticket を作る。申込に「支払い待ち」の状態は持たない。失敗→再試行は新しい Payment を作る。入金先はイベントごとに指定（Phase 8 で有効化）。

ルール

  • providerRef は一意（Webhook が二重に届いても状態を二重に進めない）
  • PENDING かつ holdExpiresAt 前の Payment は定員に数える。期限切れは Cron で EXPIRED にして answersDraft を消す
  • 支払い済みの Payment があるイベントは移管できない
  • 返金は MVP では持たない（運営が決済事業者の管理画面で対応）

画面との対応

  • モック決済・確認中・参加予定（決済完了）・失敗
  • 参加者リストの支払い状況

06

制約とインデックス

Prisma で表現できないものは、マイグレーションに SQL で追記する（schema.prisma 末尾にコメントで記載）。

対象内容理由
Slot・Event（排他）申込処理で SELECT … FOR UPDATE してから、参加予定と決済中の確保（Payment PENDING）を数える新歓期の同時申込で枠の定員・全体の上限を超えない（§7）
Registration部分一意インデックス (slotId, userId) WHERE status = 'CONFIRMED'同じ枠は1人1件。キャンセル後の再申込は許可
Ticket(eventId, userId) 一意、token 一意1人1イベント1枚。QR の値は推測できないものにする
RegistrationQuestion部分一意インデックス (eventId, commonKey) WHERE commonKey IS NOT NULL共通の質問はイベントごとに1つずつ
OrganizerCHECK (type = 'USER') = (userId IS NOT NULL)、slug 一意、予約語はアプリで拒否個人と団体の差を型で守る
EventCHECK answerRetentionDays IN (30, 90, 365)、CHECK capacity IS NULL OR capacity >= 1保持期間の選択肢（§8）・全体の上限
SlotCHECK capacity >= 0 AND priceYen >= 0不正値の防止
PaymentproviderRef 一意Webhook の冪等性（§9）
Cron 用Payment(eventId, status, holdExpiresAt)、Event(endAt)席の確保の期限切れ、回答の自動削除と7日前予告
一覧・検索用Event(status, startAt)、Event(genreId, startAt)、Event(area, startAt)、Slot(eventId, kind)、pg_trgm の GIN（title）ジャンル・地域・参加枠の絞り込み、カレンダー、キーワード検索
通知NotificationLog(userId, createdAt)、(type, status)再送・配信状況の確認
