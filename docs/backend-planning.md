# NMJ 要件定義と Stripe 環境 DB の打ち合わせメモ

実装方針はHono・HonoX・Cloudflareを前提に、[実装計画](implementation-plan.md)へ整理した。

まず公開範囲と決済の責任分担を決め、その条件で DB と API の仕様を固める。以下の「既存設計」は資料に記載された方針であり、実装・申請・本番稼働の完了を意味しない。「提案」「要確認」は打ち合わせで決める。

## 打ち合わせで最初に話すこと

> 現在は申込・決済・QR受付までのDBドラフトがあります。先に決めたいのは、公開時にどこまで提供するか、有料イベントの売上を誰が受け取るか、返金と決済中の席確保をどう扱うかです。そこが決まれば、DBとAPIを固めて、フロントから接続できる状態に進められます。

| 順番 | 話すこと | 持ち帰る結論 |
| --- | --- | --- |
| 1 | 公開時の機能と日程 | 初回リリースの対象と後回しの機能 |
| 2 | Stripe の申請と売上の流れ | 申請者、契約主体、団体への入金方法、確認担当 |
| 3 | 申込・決済・キャンセルのルール | 席確保期限、返金条件、中止時の対応 |
| 4 | 環境と DB | 採用サービス、権限、DB確定に必要な残課題 |
| 5 | デザイナーとの接続 | 必要な画面状態、API仕様の共有日 |

## 要件定義で固める内容

### 既存設計の軸

以下は複数枠を選べる従来のドラフト。今回の方針は「1アカウント・1イベント・1価格枠」に変更する。スキーマ自体はまだ変更していない。

- 権限は NMJ運営の ADMIN、団体の OWNER、一般 USER。団体OWNERは複数可。
- イベントに学生・大人・懇親会などの参加枠を設定し、枠ごとの価格と定員、イベント全体の上限を持つ。
- 無料のみの申込はその場で確定。有料枠を含む場合は決済完了を確認してから全枠を確定する。
- 参加申込の状態は参加予定とキャンセルのみ。補欠と参加者向けの支払い待ち状態は持たない。ただし決済処理には PENDING が必要。
- QRチケットは1人1イベント1枚。複数枠に申し込んでも1枚で、受付状態の変更履歴を残す。
- 本名などの申込回答は RegistrationAnswer に保存し、保持期間後に削除する。Userには認証用メール等を持つ。
- 団体フォロー、イベント保存、お知らせ、記事の投稿・審査も既存設計に含まれる。初回公開に含める範囲は再確認する。

### 現時点の確定事項と方針

- 確定：1アカウント・1イベントにつき本人分1枚、価格枠は1つ。
- 方針：収集情報は基本的に公開を想定し、電話番号・メールアドレスは非公開。
- 未確定：具体的な公開項目。公開プロフィールと参加者一覧・参加履歴・申込回答は分けて決める。
- 提案：不要な情報は集めず、公開項目を固定する。認証・決済情報やQRトークン等の内部情報は公開対象に含めない。

### 次に詰める仕様と推奨案

推奨案は未承認。まず優先度1を決め、その後に運用条件を固める。

| 優先度 | 決める仕様 | 確認する内容 | 推奨する初回の案 |
| --- | --- | --- | --- |
| 1 | 収集項目と公開範囲 | 本名・所属は必要か。参加者一覧、参加履歴、申込回答を誰に公開するか | 公開プロフィールの項目を固定。電話は必要時のみ。申込回答の一律公開は避ける |
| 1 | 公開の確認と変更 | 公開される情報をどこで確認させるか。後から非公開・削除できるか | 保存・申込前に公開項目を表示。公開後の変更方法も用意 |
| 1 | 販売と入金の主体 | NMJか各団体か。手数料・返金・問い合わせを誰が担うか | 資金の流れと責任分担を先に1枚にまとめ、Stripe構成を決める |
| 1 | キャンセルと返金 | 自己都合、中止、重複・遅延決済、返金失敗時をどう扱うか | 場合ごとに条件・担当・通知を決める。価格枠の直接変更は初回対象外 |
| 1 | 枠と懇親会の関係 | 本編＋懇親会を買えるか。セット間で定員を共有するか | セット販売が必須か先に確認。単純な1枠購入で表せる範囲に絞る |
| 1 | 席確保と再申込 | 何分確保するか。開始後の取り消し、期限切れ、キャンセル後の購入を認めるか | 最終確認後に確保。既存の手続きがあれば案内。期限はStripeの条件と照合して決定 |
| 2 | 権限と重要操作 | owner全員に回答閲覧・CSV出力・入金先変更を許すか。受付専用担当は必要か | 権限表を作成。受付担当にownerの全権限を渡す必要があるか確認 |
| 2 | 保持期間と退会 | 回答、連絡先、決済記録、監査ログ、出力CSVをいつまで残すか | データの種類ごとに期限と削除担当を決定。退会と決済履歴の削除を分ける |
| 2 | 異常時の対応 | 誰に通知し、誰が販売停止・解除するか。止めても継続する処理は何か | 新規販売だけを停止可能にし、進行中決済の確認は継続 |
| 2 | 利用規模と不正利用 | 最大参加人数、販売開始時の集中、仮押さえの繰り返しをどう扱うか | 1アカウント1枚を基準とし、操作別の制限を負荷検証で調整 |
| 2 | 開催回の単位 | 同じ企画の別日・別時間を別イベントとして購入できるか | 開催回ごとにEventを分け、制約はuserIdとeventIdで適用 |
| 1 | 初回公開の範囲 | 有料決済・複数団体への入金・記事・通知・Wallet等のどこまで必要か | 必須機能と後続機能を分け、完成条件と日程を確定 |

WAFの製品選定、具体的な回数制限値、インデックス名などは実装側で検討する。仕様として先に決めるのは、公開範囲、操作権限、購入ルール、運用担当、想定規模。

## 映画館を参考にしたチケット申込フロー

### 今回の要件

1アカウントから1イベントに申し込める価格枠は1つとする。イベントには学生・一般など複数の価格枠を登録できるが、参加者はそのうち1つだけを選ぶ。枚数は本人分の1枚固定とする。代理購入や複数枚購入はこの案には含めない。

同じイベントに複数の開催回がある場合は、開催回を独立したEventとして扱う案。現在のEventは開始・終了日時を持つため、重複判定は日付ではなくeventIdで行う。「同じ日」だけでは別イベントまで制限してしまう。

### 映画館の購入フローから取り入れること

[TOHOシネマズの公式購入案内](https://www.tohotheater.jp/vit/vit_buy.html)では、劇場・作品と日時・座席を選び、券種選択、個人情報入力、支払い、発券へ進む。一度に6枚まで指定できるため、「1アカウント1枚」は映画館の共通ルールではなくNMJ独自の要件になる。

[シネマサンシャイン公式FAQ](https://portal.cinemasunshine.smart-spoke.com/qa/)も座席指定と1回6枚までの購入を案内している。NMJでは購入対象を先に確定し、必要情報・支払い・チケット表示へ進む順序を参考にする。各社内部のDB制約や複数タブ対策は公開案内からは判断できない。

### 参加者向けの推奨フロー

| 段階 | 画面と操作 | サーバーで行うこと |
| --- | --- | --- |
| 1 | イベント詳細で価格枠を1つ選ぶ | 公開状態・受付期間・残数を表示。選択はラジオボタン |
| 2 | ログイン後、共通質問・追加質問へ回答 | 本人と選択枠を検証。ここでは席を確保しない |
| 3 | 日時・枠・金額・回答・キャンセル条件を確認 | 表示中の残数は確約ではない旨を表示 |
| 4 | 「支払いへ進む」または無料の「申し込む」 | ロック下で確定済み申込・既存手続き・定員を再確認 |
| 5 | 有料ならStripe Checkoutへ | PENDINGを作って1席確保。無料なら直ちに申込確定 |
| 6 | 支払い後に確認中画面、その後QR表示 | 支払い確認後、申込・QRを重複なく作成。未確認なら確認中のまま |

枠選択・質問回答中から席を確保すると、入力放置で定員が埋まる。まずは最終確認後に確保する案を採用候補とする。映画館の座席確保時間をそのまま転用せず、Stripe Checkoutの設定条件と合わせて期限を決める。

### 主催者がチケットを登録するフロー案

「チケット登録」を主催者側の登録という意味でも整理する。

1. イベント名・開催日時・会場・イベント全体の定員を入力する。
2. 学生・一般などの価格枠を追加し、名称・価格・定員・受付期間・対象条件を設定する。
3. 共通質問に加え、追加質問と個人情報の利用目的・保持期間を設定する。
4. 有料枠がある場合は入金先と決済利用可否を確認し、キャンセル条件を設定する。
5. 参加者側の表示と申込手順をプレビューして公開する。

「懇親会」が本編への追加購入を意味する場合、1イベント1枠のルールと衝突する。本編のみ／本編＋懇親会を別の価格枠として登録する案が簡単。ただしセット間で本編や懇親会の共通定員を持つ場合は、価格枠とは別の在庫管理が必要。初回はセット販売の要否を確認する。

### 複数タブへの対応と部分一意インデックス

同じ利用者・イベントでPENDINGを1件にする制約は、既存スキーマ末尾にもコメントとして存在する。実マイグレーションで次を適用する方針。

```sql
CREATE UNIQUE INDEX payment_pending_unique
ON "Payment" ("userId", "eventId")
WHERE status = 'PENDING';
```

PostgreSQLの[部分一意インデックス](https://www.postgresql.org/docs/current/indexes-partial.html)は条件を満たす行だけに一意性を適用できる。通常のインデックスではなくUNIQUEが必要。この制約で防げるのはPENDINGの重複であり、別ステータスの決済や確定申込との重複は別途防ぐ。

| 状況 | APIの扱い | 参加者への表示案 |
| --- | --- | --- |
| タブAで開始し、タブBでも申し込む | 一意制約の競合を捕捉し、本人の既存手続きの状態を取得。競合は409等の業務エラーへ変換 | 「このイベントの購入手続きが進行中です」＋「手続きを確認する」 |
| 同じ開始リクエストが再送される | 同じ処理キーなら既存の結果を返す | エラーにせず、同じ手続きへ戻す |
| タブAで既に購入完了している | 確定申込を返し、新規決済を作らない | 「申込済みです」＋「チケットを見る」 |
| 期限時刻を過ぎたがStripe状態が未確認 | 未払いと断定せず、先に状態確認と必要な失効処理 | 「購入状況を確認しています」＋再確認 |
| 元の購入をやめて違う枠にしたい | 元のCheckoutが支払い不能になったことを確認後、席を解放して選び直す | 「現在の手続きを取り消して選び直す」 |

タブBで制約違反が起きても、タブAの手続きを勝手に失効させない。画面のボタン無効化だけでなくDBで防ぎ、制約名を見て想定した競合だけを上記表示に変換する。DBエラー本文は表示しない。トランザクション中の一意制約違反はロールバックしてから既存手続きを取得する。

### 1イベント1枠に合わせるDB変更案

- Payment.slotIdsの配列を単一のslotIdと関連へ変更する。決済金額はサーバーで取得し、購入時の価格を保存する。
- RegistrationにもeventIdを持たせ、有効な申込に対して(userId, eventId)の部分一意インデックスを設ける。現在の(slotId, userId)制約だけでは別枠への重複申込を防げない。
- RegistrationのeventIdとslotIdが同じイベントを指すことは、Slot側の複合一意キーと複合外部キー等で保証する。単にeventId列を追加するだけでは不整合が起きる。
- 無料申込・決済開始・Webhook確定を同じEvent行のロックで直列化し、その中で本人の確定申込とPENDINGを再確認する。PaymentとRegistrationの別テーブルにある制約だけでは、両方をまたぐ競合は防げない。
- DBで席を確保する処理をコミットした後にStripeのセッションを作成し、Payment IDをもとにした冪等キーを使う。Stripe作成後・DB保存前の障害を復旧できるよう、providerRef未設定の準備段階と照合処理を設計する。現在の必須providerRefのままではこの順序に対応できない。
- FAILEDへの変更だけで席を解放しない。カード失敗後もCheckoutで再試行できるケースを考慮し、支払いが可能なセッションを残したまま新しい決済を作らない。
- 時刻が過ぎてもPENDINGの一意制約は自動では外れない。決済結果を確認してEXPIRED等に更新する処理が必要。定員計算でも、時刻だけを見て席を再販売しない。

この変更案は [DB設計 v0.5](db-design.md) と [schema.prisma](schema.prisma) に反映した（2026-11-27）。懇親会の扱いなど未決の点は仮置きで、ER図は未更新。

## 疑問点と実装が重くなる箇所

### 先に決めたいこと

| 疑問点 | 現時点の推奨案 | 理由 |
| --- | --- | --- |
| 購入枚数 | 確定：1アカウント1イベント1枚 | 代理購入や同行者の複数枚購入は扱わない |
| 懇親会も同じイベントの別枠か | 本編の価格枠とは切り分け、初回の販売対象に含めるか決める | 本編と懇親会の両方に参加する場合、単純な1枠選択では表せない。別イベント化なら申込・決済も別になる |
| 一度買った価格枠を変更できるか | 初回は直接変更できない仕様 | 差額決済・返金・在庫の移し替えを省ける |
| キャンセル後に再購入できるか | キャンセルと返金の扱いを決めてから確定 | 返金せず買い直すと同じイベントで二重負担になる |
| 入力中から席を確保するか | 最終確認後に確保する | 長時間の仮押さえを避けられる。入力後に満員になる可能性は画面で案内する |
| PENDINGがあるとき別タブでどうするか | 新規作成を止め、既存の手続きを確認する導線を表示 | タブ同士で手続きを取り消し合う挙動を避ける |

### 実装負荷と削れない部分

| 項目 | 負荷 | 重くなる理由と初回の方針 |
| --- | --- | --- |
| 1イベント1価格枠の選択 | 小 | ラジオボタンとサーバー検証。複数枠購入より単純になる |
| PENDINGの部分一意インデックスと競合表示 | 小 | 制約作成と想定した重複エラーの変換。必要な対策として入れる |
| 同時申込時の定員保証 | 中 | 別ユーザーの競合は一意制約で防げない。無料・有料で共通のロックと定員判定が必要 |
| DBとStripe間の処理復旧 | 大 | DB保存とStripeへの通信は一括でコミットできない。通信タイムアウト・再送・保存失敗を復旧する冪等キーと照合処理が必要。省略しない |
| 決済完了と期限切れの競合 | 大 | 期限切れと判断した直後に支払いが確定する可能性がある。Stripe側の状態を確認してから席を解放する。定期処理とWebhookの重複実行にも対応する |
| 複数団体への売上入金 | 大 | Connectの登録・利用可否・追加確認・権限・手数料・返金責任まで決める必要がある。複数団体への入金が公開要件なら初期から設計する |
| 本編と懇親会のセット販売 | 大 | 複数の価格枠が同じ本編定員や懇親会定員を消費する場合、共通在庫の管理が増える。単に価格枠を増やすだけでは対応できない |
| 枠変更・部分返金 | 大 | 金額と在庫と参加資格を同時に更新する必要がある。初回は枠変更と部分返金の対象を絞る |

負荷が高い処理のうち、決済の復旧・定員保証・期限切れの整合性は、販売対象を絞っても必要。主催者への自動入金、枠変更、セット販売は、事業上の要件に応じて範囲を調整できる。

初回構成の推奨案は「本人分1枚・価格枠1つ・枚数変更なし・直接の枠変更なし・最終確認後に席確保・進行中の手続きは再利用」。返金を管理画面で行う場合も、結果をDBへ反映し、参加資格と一致させる運用は必要。

## Stripe の準備と論点

### 仕組みの説明

Checkoutは支払い画面、Connectは複数の主催者アカウントや売上の分配を扱うための仕組み。WebhookはStripeから支払い結果などをサーバーへ知らせる通知。既存設計は、画面の「支払い完了」表示だけでは参加を確定せず、Webhookで支払いを確認する方針。

Connectで複数アカウントを扱う構成は[Stripe公式のConnect資料](https://docs.stripe.com/connect)を参照。Standardはスキーマ上の想定で、採用構成や課金方式は未確定。

### 申請と事業側への確認

- NMJ側の契約主体、申請者、管理者、申請日、現在の審査状態。
- 法人・団体情報、代表者の確認情報、入金口座、サイトURLを誰が準備するか。
- 学生団体・任意団体・未成年の代表者を、今回の国・事業形態・Connect構成で扱えるか。Stripeへの確認結果を記録するまで登録可能と断定しない。
- 登録できない団体は無料イベントのみとするか、別の運用を用意するか。
- 決済手数料、Connect関連費用、NMJの運営手数料を誰が負担するか。料金は構成確定後に公式料金・契約条件で確認し、確認日と計算例を残す。
- 特商法表記、利用規約、プライバシーポリシー、キャンセル方針の作成担当と確認期限。

### 技術側の準備案

1. 検証用のSandboxを用意し、本番とキー・Webhook設定・データを分ける。Stripe公式は新規連携で一般のSandboxの利用を案内している。[検証環境の説明](https://docs.stripe.com/testing-use-cases)
2. サーバーからCheckoutを作成し、金額はDBの価格から計算する。選んだ枠・金額・入金先の記録を決済開始時に固定する。
3. Webhookの署名を検証し、重複・再送・順序の逆転があっても同じ申込を重ねて作らない。受信イベントIDと処理結果の保存方法を決める。[Webhook公式資料](https://docs.stripe.com/webhooks)
4. 決済期限と席確保期限を揃える。Stripeの状態を確認できない場合は、未払いと断定して席を解放しない。
5. 支払い成功・失敗・期限切れ・Webhook再送・遅延・返金・団体の入金不可を検証し、記録と通知まで確認する。

秘密キー、Webhook署名シークレット、本人確認書類、口座情報そのものはこのメモや公開用docsに書かない。必要な権限や保管先だけを記録する。

## セキュリティ対策の案

監査ログ、不正なAPI入力の検知、大量アクセスの制限に加え、他人の情報に触れない権限設計、決済の改ざん防止、情報漏えい時の復旧までを対象にする。以下は採用案であり、導入済みの対策ではない。

### 情報公開と収集範囲の方針

利用者からの方針：収集情報は基本的に公開情報として扱い、電話番号・メールアドレスは非公開とする。

公開は漏えい対策の代わりにはならない。公開情報は第三者による取得・転載が可能で、後から非公開に戻しても外部のコピーは回収できない。セキュリティ負担を減らすには、公開してよい情報だけを最小限集め、公開項目を固定する案が適している。

以下は実装案であり、公開項目の確定ではない。

| 情報 | 扱いの案 |
| --- | --- |
| 公開用ニックネーム・自己紹介 | 公開プロフィールの項目として、保存前に公開範囲を明示 |
| 本名・所属・参加イベント | 個別に公開の要否を決める。プロフィールの公開と参加履歴の公開は分ける |
| 主催者が追加する質問への回答 | 一律公開にせず、初回は非公開または質問項目を限定。自由記述には連絡先等が書かれる可能性がある |
| 電話番号・メールアドレス | 非公開。電話番号は用途が必要な場合だけ収集し、閲覧権限を限定 |
| 認証情報・決済識別子・QRトークン・監査ログ | 内部情報として非公開。一般公開データに含めない |

公開範囲は「未ログインでも公開」「ログイン利用者のみ」「当該イベント参加者のみ」「主催者と本人のみ」「運営のみ」を区別する。本名、所属、参加者一覧、参加履歴、申込回答の各項目について範囲を決める。利用者が保存・申込する前に項目ごとに公開範囲が分かる表示を用意する。

APIでは公開フィールドを明示的に列挙する。DBの全列を返して電話・メールだけを除く実装は避け、新しい内部項目が追加されても公開されないようにする。

### 初回公開に含める対策

| 対策 | NMJでの具体例 | 負荷の目安 |
| --- | --- | --- |
| 対象データごとの権限確認 | リクエストの団体ID・申込IDを信頼せず、ログイン本人がその団体のownerか、申込本人かを毎回確認。CSV、QR受付、回答閲覧にも適用 | 中。API全体で共通化する |
| 入力と出力の許可リスト | 型、文字数、件数、列挙値、JSONサイズ、HTTPメソッドを検証。許可していないrole・price・status等は更新させない。公開APIで回答やメールを返さない | 小〜中 |
| 決済の改ざん・偽装防止 | 価格はDBから計算。Webhook署名・支払い状態・金額・通貨・決済ID・対象アカウントを照合。イベント重複と再送を処理 | 中〜大。既存の決済設計に組み込む |
| 管理者とセッションの保護 | インフラ・Stripe・認証管理者にMFA。アプリ管理者にも強い認証を適用。CookieのSecure・HttpOnly・適切なSameSite、ログアウト・権限変更時のセッション失効を設計 | 中 |
| ブラウザ経由の攻撃対策 | Cookie認証の更新APIにCSRF対策。イベント本文のMarkdown・HTMLを安全に表示しXSSを防ぐ。CSPを設定。SQLはパラメータ化 | 中 |
| WAFとAPI制限 | CDN/WAFで既知の攻撃・大量通信を軽減し、アプリ側でも操作別に制限。IPだけでなくアカウントと対象イベント等で判定 | 中。配信基盤に依存 |
| 監査ログと通知 | 誰が・いつ・何を対象に・何を実行し・成功したかを記録。入金先変更、owner追加、CSV出力、返金、運営権限変更は重点記録 | 中 |
| 秘密情報とDBの保護 | 秘密キーはサーバー側の秘密管理へ。DBへの不要な公開アクセスを防ぎ、実行用とマイグレーション用の権限を分ける。本番・検証を分離 | 中 |
| 更新・検査・復旧 | 依存関係と秘密情報の自動スキャン、重要修正の適用、バックアップと復元確認、障害時の連絡・停止・復旧手順 | 中。継続運用が必要 |

権限確認とリソース消費制限の考え方は[OWASP API Security](https://devguide.owasp.org/en/07-training-education/07-api-top-ten/)を参照。WAFだけでは、正しい形式で他人の申込を取得するような業務権限の不備は防げない。

### 異なるリクエストが来たときの扱い

「いつもと違う」だけで自動遮断せず、拒否条件が明確なものと、異常の傾向を分ける。

| リクエストや兆候 | 対応案 |
| --- | --- |
| 想定外のフィールド、型、巨大な本文、不許可メソッド | 入力を拒否し、理由コードと経路を記録。繰り返しで通知 |
| 他団体の参加者や他人の回答へのアクセス | 権限判定で拒否し、反復を検知。情報の存在を漏らさない応答を設計 |
| 決済署名不正、金額や対象アカウントの不一致 | 申込を確定せず記録・通知 |
| 403や404の急増、IDを順番に探索するアクセス | 回数・時間帯・対象範囲を集計し、制限や調査につなげる |
| 多数のIPから同じ操作・イベントへの集中 | IPごとの制限に加え、対象単位・操作全体の上限と処理待ち件数を確認 |
| 大量のCSV出力、owner追加直後の入金先変更 | 監査通知し、重要変更には再認証を要求する案 |

リクエスト本文全体の記録は避ける。監査ログはrequestId、操作者ID、操作名、対象ID、時刻、結果、理由コードを中心とし、必要に応じてIP等をアクセス制限・保持期限付きで扱う。トークン、Cookie、秘密キー、QRの生トークン、申込回答を記録しない。ログは閲覧・削除権限を限定した保存先へ送り、重要ログの欠落も監視する。[OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

### 大量アクセスと買い占めへの対策

- 閲覧・検索・ログイン・申込・Checkout作成・メール送信・CSV出力それぞれに上限を設ける。静的コンテンツはCDNキャッシュし、重い検索はページサイズ・タイムアウト・同時実行数も制限する。
- 制限超過時は429と再試行の案内。複数サーバー間で共有できる制限を用い、信頼できるプロキシ経由のIPのみ採用する。大学などの共有回線を一律に遮断しない。
- PENDINGの一意制約は同一アカウントの重複防止。別アカウントでの大量確保は防げないため、確保期限、繰り返し失効する利用者の開始制限、必要な箇所のBotチャレンジを組み合わせる。
- 正常な販売開始の集中と攻撃を区別できるよう、制限値は想定人数・負荷検証で決める。通知・制限をAPI単位で調整できるようにする。
- Stripe Webhookは通常APIと別のポリシーにする。正当な再送・集中を誤遮断しない容量と処理待ち管理を用意し、署名検証と安全な永続化を優先する。[Stripe Webhook公式資料](https://docs.stripe.com/webhooks)

### 公開後に段階的に追加する候補

振る舞いを分析する不正検知、ログを横断するSIEM、高度なBot対策、販売開始時の待合室、外部の侵入テスト。最初から独自の異常検知基盤を作ると、誤検知の調整と監視運用が重い。まず明確な権限・入力制約と既存基盤のWAF・監視を使い、実測を見て追加する。

### 異常時に実行できる操作

新規申込・決済開始・CSV出力を個別に止めるスイッチ、セッション失効、キーの失効と交換、ログ保全、関係者への連絡手順を用意する。新規販売を止めても、進行中の決済を確認するWebhookと照合処理は継続できる設計にする。バックアップ復元は手順だけでなく実際に検証する。

## DB の設計と確定前の確認

正となるドラフトは [schema.prisma](schema.prisma)（v0.5）、変更の理由・公開範囲・未決事項は [DB設計](db-design.md)。[ER図](er-diagram.html) は v0.4 のまま。

| データ | 役割 |
| --- | --- |
| User / Organizer / OrganizerMember | ログイン利用者、個人・団体の表示情報、団体の操作権限 |
| Event / Slot | イベントと参加枠。公開状態・価格・定員を管理 |
| Payment | 支払いと決済中の席確保。失敗・期限切れ・返金も記録 |
| Registration | 枠ごとの確定した参加申込とキャンセル |
| Ticket / CheckinLog | 1人1イベントのQRと受付変更の履歴 |
| RegistrationQuestion / RegistrationAnswer | 申込質問と回答。回答には保持期間を適用 |
| PayoutAccount | 主催者とStripe側アカウントの関連付け |
| NotificationLog / AnswerExportLog | 通知の送信記録と回答の出力記録 |

### DB を確定する前に確認すること

- 定員判定と席確保・申込作成を同じトランザクションで処理する。イベントと複数枠のロック順序も統一する。
- スキーマ末尾のCHECK制約と部分一意インデックスはコメントなので、実際のマイグレーションへ含める。
- Payment.providerRefの一意制約だけでWebhookの二重処理は防げない。決済状態の条件付き更新、受信イベントの記録、申込・QR・通知の冪等性を設計する。
- Payment.slotIds と answersDraft は配列・JSON。枠と質問が対象イベントに属すること、必須回答、対象枠、権限をサーバー側で検証する。
- 決済時点の枠別価格・合計・手数料・入金先の保存方法を決める。後の価格変更で決済履歴の意味が変わらないようにする。
- 部分返金や返金失敗を扱う場合、現状のREFUNDEDとrefundedAtだけで足りるか確認する。
- PayoutAccount.verifiedAtだけで運用できるか確認する。入金・決済の可否や追加確認要求など、必要な状態を決める。
- 決済中の回答下書きも個人情報として扱い、FAILEDで残った下書きとログ・バックアップを含めた保持方針を決める。
- 大学マスタ、補欠廃止後のincludeWaitlist、団体削除・退会・再申込時のQRの扱いを整理する。

### 受け入れ条件のたたき台

- 最後の1席へ同時申込しても定員を超えない。
- 同じWebhookを繰り返し受けても申込・QR・通知が重複しない。
- 決済画面を閉じた場合や通知が遅れた場合も、決済と席数が一致する。
- 他団体の参加者情報や回答を閲覧・出力・受付変更できない。
- 全枠キャンセル後はQRを使えず、再申込時の扱いが仕様どおりになる。
- 回答と決済中の下書きが、それぞれ決めた期限で削除される。
