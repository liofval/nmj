§1プロダクトの定義

主催者が主語になるイベントプラットフォーム。主催者は学生団体でも個人でもよく、どちらもフォローの対象になる。学生は主催者をフォローすることで、その主催者の新しいイベントを継続的に受け取る。

主軸は学生団体に置く。学生団体には他のコミュニティにない事情が三つあり、そこに構造で応えることが差別化になるためである。

  • 幹事が毎年交代する。 イベントが個人アカウントにぶら下がる設計では、代替わりのたびに過去の実績とフォロワーが失われる
  • 同じ団体が繰り返し開催する。 新歓、定例会、合宿、追いコン。過去イベントの複製と、フォロワーへの自動告知が効く
  • 新入生は個別イベントではなく団体を探している。 発見の単位はイベントより先に団体である

一方で、入口は個人主催に開く。「サークルを立ち上げる前に、まず一本イベントを立てる」は学生では頻繁に起きる。個人で始めた人が後から団体を作り、過去のイベントごと団体へ移せる導線が、団体という主軸への流入路になる（§6 UC-5）。

ひとことで

「connpass の参加枠モデルを、学生の主催者フォロー構造と少額決済に載せ替えたもの」。

発見1 — 低額イベントで既存サービスの手数料構造が壊れる

学生イベントの参加費は 500〜2,000 円が中心。Peatix の「4.9%＋99円/枚」を当てはめると、固定費が効いて低額ほど不利になる。

connpass がプラットフォーム手数料を取らず決済手数料のみで運用しているのは、この価格帯を成立させる合理的な判断である。学生特化を名乗る以上、枚あたり固定費を持たない手数料設計を前提にする。

発見2 — ペインは「集客」ではなく「集金と会計」に寄っている

集金まわりの調査で繰り返し現れた課題:

  • 会計担当が立て替え、後から回収する負担
  • 誰が払ったか分からない、釣り銭の準備が要る
  • 未払いの催促が気まずく、放置される
  • 出欠と支払い状況が別管理で、会計が合わない

connpass も Peatix も Luma も、ここは「決済して終わり」で団体の会計には踏み込んでいない。参加登録と入金状況が同一のデータとして紐づく状態は、既存サービスの空白地帯である。今回の差別化軸は団体ページとフォローに置くが、この空白は次の拡張候補として意識的に残す（§14）。

発見3 — 縦割り特化は日本のこの市場で実証済み

connpass は「エンジニア勉強会」という縦を切って汎用の Peatix と共存している。一方 Luma は無料・高デザインで横から侵食してくるため、「きれいなイベントページ」の土俵では勝負にならない。新歓・学園祭・幹事交代・大学単位のつながりといった学生固有の文脈に踏み込むほど差別化が効く。

前提リスク

Luma が日本の学生コミュニティに先に浸透した場合、「イベントページを作る」だけの価値は消える。団体・フォロー・大学という構造を早期に立てられるかが分岐点になる。

§3ターゲットと利用文脈

主催者 — 学生団体の運営メンバー

サークル代表、幹事、広報担当。年に数回〜十数回のイベントを開催する。Google フォームで申込を集め、LINE で告知し、参加費は当日現金か個人の PayPay で回収している。表計算ソフトで名簿を管理し、当日は印刷した紙で受付する。

主催者 — 個人で動く学生

団体に属さずにイベントを企画する学生。勉強会、読書会、交流会、有志の合宿。「まず一本やってみる」段階にあり、団体を作るほどの体制はない。ここで手応えを得た人が団体を立ち上げ、イベントごと移管していく（§6 UC-5）のが、団体という主軸への流入路になる。

参加者 — 学生

大半がスマートフォンからアクセスする。新入生は「何かサークルを探している」漠然とした状態で流入し、既存の学生は「フォローしている団体の次のイベント」を目当てに戻ってくる。

需要の季節性

新歓期（3月下旬〜5月上旬）に開催数とアクセスが集中する。この期間の体験がプロダクトの評価を決めるため、初回リリースは新歓期に間に合わせることが実質的な納期になる。

§5ドメインモデル

中心にあるのは Organizer → Event → Slot → Registration の階層である。

Organizer を第一級のエンティティにする

主催者が団体と個人の二種類あるとき、Event に groupId と userId を並べて片方だけ埋める設計は採らない。イベント・フォロー・入金先・権限判定のすべてに「団体か個人か」の分岐が入り込み、機能を足すたびに分岐が増殖するためである。

代わりに Organizer（主催者アカウント）を独立したエンティティとし、その下に団体と個人の違いを閉じ込める。ユーザー登録時に type=USER の Organizer を自動生成し、団体作成時に type=GROUP の Organizer を生成する。イベント・フォロー・入金先・告知はすべて Organizer だけを参照する。

プロフィールがアイコン・ユーザーネーム・あだ名・SNS リンクの4項目に絞られた結果、団体固有の属性は残らなくなった。したがって Group という別テーブルは設けず、Organizer に一本化する。団体と個人の差は type と、運営メンバーを持てるかどうかだけになる。

設計判断

参加登録は Event ではなく Slot にぶら下げる。定員も価格も枠の属性であり、イベント直下に定員を置くと「懇親会だけ有料」「LT 登壇者枠は 5 名」といった学生イベントで頻出する形が表現できなくなる。

権限判定

イベントの編集・参加者の閲覧・入金先の設定は、すべて次の1関数を通す。分岐を知っているのはこの関数の内部だけとする。

async function canManage(organizerId: string, userId: string): Promise<boolean> {
  const organizer = await db.organizer.findUnique({ where: { id: organizerId } })
  if (!organizer) return false

  // 個人主催者 — 本人のみ
  if (organizer.type === 'USER') return organizer.userId === userId

  // 団体主催者 — OWNER または ADMIN
  const member = await db.organizerMember.findUnique({
    where: { organizerId_userId: { organizerId, userId } },
  })
  return member?.role === 'OWNER' || member?.role === 'ADMIN'
}
大学はイベントが持つ

大学はプロフィールではなく Event.targetUniversityId が持つ。学生は他大学のイベントにも参加し、学外に開かれた合同イベントもあるため、主催者の所属で絞るよりイベント自身が対象を宣言するほうが実態に合う。マイページの項目も4つのまま増えない。NULL は「大学を問わない」を意味する。

§6主要ユースケース

UC-1 一本線（MVP の受け入れ基準）

  1. 01主催者Google でログインし、団体を作成。副代表を管理者として招待する
  2. 02主催者新歓イベントを作成。一般枠 40 名（無料）と懇親会枠 20 名（1,500 円）を設定し、アレルギーの質問を追加して公開
  3. 03システム団体のフォロワーへ公開を通知
  4. 04参加者イベントを見つけて両方の枠に申込。質問に答え、懇親会枠は決済へ進む
  5. 05参加者支払い完了。参加確定となり、マイページに表示される
  6. 06主催者当日、スマホで参加者リストを開き、来た人をタップして受付済にする

UC-2 満員と繰り上げ

定員に達した枠への申込は補欠として受け付ける。確定者がキャンセルすると、同じ枠の補欠の先頭が自動的に繰り上がり、本人へ通知される。有料枠の繰り上げでは支払い期限が設定される（§7）。

UC-3 幹事の代替わり

卒業する代表が、新代表を OWNER に昇格させてから団体を離脱する。団体・過去イベント・フォロワーはすべて残る。最後の OWNER は離脱できない制約により、管理者不在の団体は発生しない。

UC-4 イベント中止

主催者がイベントを中止すると、全参加者へ中止通知が送られ、以後の申込が停止する。有料枠の返金は原則行わない。中止に伴う返金が必要な場合、運営が決済事業者の管理画面から個別に対応する（MVP では機能として持たない）。

UC-5 個人イベントの団体への移管

個人としてイベントを立てた学生が、後日サークルを正式に立ち上げ、そのイベントを団体主催に移す。参加者・申込・支払い状況はそのまま引き継がれ、イベントの URL も変わらない。

  • 実行できるのは、移管元と移管先の両方で canManage が真の人のみ。自分が管理していない団体へイベントを押し付けることはできない
  • 支払い済みの Payment が1件でも存在するイベントは移管できない。 入金先が変わることで、決済事業者側の記録と齟齬が生じるため。この制約は Phase 4 以降で効く
  • 移管によってフォロワーへの再通知は行わない。新しい主催者のフォロワーに知らせたい場合は、主催者が明示的に告知する

逆方向（団体 → 個人）も同じ関数で扱えるが、UI としては提供しない。誤操作で団体の資産が個人に移ることを避けるためである。

規則

  • 先着順。 抽選は MVP の対象外
  • 定員判定は必ずトランザクション内で行う。 枠行をロックしてから確定数を数え、登録を作成する。アプリケーション側で件数を数えてから書き込む実装は、新歓期の同時アクセスで確実に定員超過を起こす
  • 補欠の順序は申込時刻。 waitlistPos は保持するが、正の順序は appliedAt とし、繰り上げ時に再計算する
  • 1ユーザーは同一枠に1件のみ。 異なる枠への同時申込は許可する（本編＋懇親会）
  • 有料枠の支払い期限は min(申込時刻 + 24時間, イベント開始時刻)。期限切れは EXPIRED とし、枠を解放して補欠を繰り上げる
  • キャンセル期限。 イベント開始後のキャンセルは不可。開始前であれば無料枠はいつでもキャンセルできる
  • 有料枠の支払い済みキャンセルは返金しない。 申込画面でこの旨を明示し、同意を得る
要検討

「支払い期限 24 時間」は、開催直前の申込では実質機能しない。開始 24 時間前を過ぎたイベントでは期限を 1 時間に短縮する、あるいは有料枠の申込を締め切る。運用データが出るまで暫定値とする。

§8申込フォームと個人情報

アカウントに本名を持たせない。 プロフィールは表示名（ハンドルネーム）・メールアドレス・大学のみとする。一方で、合宿の緊急連絡先、大学への届出、飲食を伴う会のアレルギー確認など、イベントによっては主催者が本名や連絡先を知る必要がある。

この二つを両立させるため、個人情報はアカウントではなく申込ごとの回答として持つ。誰の情報が、どのイベントのために、いつまで存在するのかが、データ構造の上で確定する。

なぜイベント単位か

学生団体の現状は、Google フォームで本名と電話番号を集め、スプレッドシートに無期限で置きっぱなしにする運用である。幹事が代替わりしても消えず、共有リンクだけが生き続ける。個人情報をアカウントに持たせず、イベントに紐づけて期限付きで持つ設計は、この状態を運用ルールではなく構造で防ぐ。既存のイベントサービスにはない性質になる。

主催者が質問を設計する

イベントごとに、主催者が申込時の質問を追加できる。ゼロから作らせないよう、よく使う項目はプリセットとして用意する。

イベント公開後は、質問の削除と型の変更を禁止する。 既存の回答と整合しなくなるためである。追加・並べ替え・文言の修正のみ許可する。

回答が見える範囲

  • 主催者（canManage が真の人）と回答した本人のみ。 それ以外からは一切見えない
  • 公開参加者リストには出さない。 公開されるのは表示名のみで、回答は主催者用の画面にしか現れない
  • CSV 出力は主催者のみ。出力の操作は記録に残す（誰がいつ出力したか）
  • イベントが中止されても、回答の閲覧権限は変わらない。保持期間の起算は当初の開催日とする

保持期間は主催者が選ぶ

イベント作成時に 30日 / 90日 / 1年 から選ぶ。既定は 30日。選択欄には、選択の重みが伝わる注釈を添える。

個人情報の保持期間

  ○ 30日（推奨）    ○ 90日    ○ 1年

  イベント終了からこの期間が過ぎると、申込時の回答は自動的に
  削除されます。参加記録と支払い履歴は残ります。

  長く保持するほど、団体として個人情報を管理する責任が重く
  なります。合宿や野外イベントのように、事後の事故対応で

  • 削除されるのは RegistrationAnswer のみ。Registration（誰が参加したか）と Payment（支払い記録）は残る
  • 参加者は自分の回答をいつでも確認・訂正でき、イベント終了後は自分の判断で削除できる

毎回入力する

回答をユーザーのプロフィールに保存して次回以降に自動入力する仕組みは持たない。保存すれば結局アカウントが本名を抱えることになり、この章の前提が崩れるためである。入力の手間はブラウザの自動入力に任せる。

主催者側に課す義務

  • isPersonalData の質問を1つでも含むイベントは、公開時に利用目的の記載を必須にする（「合宿保険の加入手続きに使用します」など）
  • 申込画面には、誰が回答を見るのかといつまで保持されるのかを、申込ボタンの手前に必ず表示する

§9決済の設計

MVP では実決済を行わないが、後から差し替えたときに参加登録側のコードが一行も変わらないことを設計目標とする。そのために、モック実装も実決済と同じ非同期フロー（外部で支払い → Webhook で状態確定）を通す。同期的に「支払い済にする」だけのモックを書くと、実決済導入時に状態遷移を作り直すことになる。

抽象化

interface PaymentProvider {
  // 支払いセッションを開始し、遷移先 URL を返す
  createCheckout(input: {
    registrationId: string
    amountYen: number
    payoutAccountRef: string | null   // イベントごとの入金先
    returnUrl: string
  }): Promise<{ providerRef: string; redirectUrl: string }>

  // Webhook を検証し、正規化したイベントを返す
  parseWebhook(rawBody: string, signature: string): PaymentEvent

  // 実装は後日。MVP では未対応エラーを返す
  refund(paymentId: string, amountYen: number): Promise<void>
}

type PaymentEvent =
  | { type: 'paid';   providerRef: string; paidAt: Date }
  | { type: 'failed'; providerRef: string; reason: string }
実装createCheckout状態確定時期

Webhook ハンドラの要件

  • 冪等であること。 Payment.providerRef にユニーク制約を張り、同じイベントが二重に届いても状態を二重に進めない
  • 署名を検証すること。 モック実装でも検証経路を通し、本番導入時に検証漏れが起きない形にしておく
  • 支払い完了で確定させること。 PENDING_PAYMENT → CONFIRMED の遷移は Webhook のみが行う。リダイレクト先の画面で確定させてはならない

入金先

入金先はイベントごとに指定できる。合宿費は会計担当の口座、学祭の物販は団体の口座、といった実態に合わせるための決定である。データモデル上は Organizer が複数の PayoutAccount を持ち、Event.payoutAccountId がそのうち一つを指す。個人主催者も同じ仕組みで入金先を持つ。MVP ではフィールドを持つだけで、UI も送金処理も実装しない。

法務上の分岐点（実決済フェーズで確定が必要）

参加費をプラットフォームが一旦預かって主催者へ送金する形は収納代行にあたり、規約・入金サイクル・未入金トラブルの責任を運営が負う。主催者の Stripe アカウントへ直接入金する形（Stripe Connect Standard）なら運営は資金に触れず、責任範囲が大きく縮む。「イベントごとに入金先を指定できる」という要件は後者と自然に両立するため、実決済は Connect Standard を第一候補とする。

個人主催者の有料イベント（実決済フェーズで確定が必要）

個人主催でも有料イベントを許可する方針を採った。ここで注意が要るのは、有料イベントの販売主体が個人になると、特定商取引法に基づく表記として氏名・住所・電話番号の開示が求められうる点である。学生が自宅住所と電話番号を公開する状況は、そのまま放置できない。

実務では、開示請求があった場合に遅滞なく提供する旨を表示することで常時掲載を省略する運用や、プラットフォームが問い合わせ窓口を代行する形が採られている。いずれを採るかは法務確認を経て決める必要があり、この要件定義では結論を出さない。 確認が済むまでは Phase 8 の有料機能を個人主催者へ開放しない、という段階的な開放も選択肢になる。
